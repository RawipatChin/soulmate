# สเปก: เข้าสู่ระบบและสลับหน้าร้านกับหลังบ้าน SOULMATE

Status: ready-for-agent

ขอบเขตระยะแรกจาก [แผนบัญชี คำสั่งซื้อ และ guest checkout](../../docs/guest-checkout-and-account-plan.md): ให้เข้าสู่ระบบได้ก่อน ส่วน flow การซื้อขายทำภายหลัง

## Problem Statement

ผู้ใช้ควรเข้าสู่ระบบบัญชีลูกค้าและผู้ดูแลระบบได้ด้วย Firebase Authentication ชุดเดียวกัน และไปยังพื้นที่ที่ตนมีสิทธิ์โดยไม่สับสน ปัจจุบันหน้าล็อกอินหลังบ้านให้เลือกประเภท `admin` หรือ `super_admin` ก่อนส่งฟอร์ม ทั้งที่สิทธิ์จริงอยู่ในข้อมูลบัญชี ผู้ดูแลระบบที่อยู่หน้าร้านยังไม่มีทางเข้าไปหลังบ้านตาม role ที่ชัดเจน และกฎข้อมูลยังมีข้อยกเว้นสิทธิ์ admin ตามอีเมล ซึ่งไม่สอดคล้องกับ role ที่ตรวจจากบัญชี

## Solution

ใช้ Firebase Authentication เดิมสำหรับบัญชีลูกค้าและผู้ดูแลระบบ แล้วอ่าน role และสถานะบัญชีจากข้อมูลที่ระบบควบคุม ให้ฟอร์มล็อกอินตรงไปตรงมาโดยไม่ต้องให้ผู้ใช้เลือก role ลูกค้าเข้าสู่ภาพรวมบัญชีที่ `/account` และแก้ข้อมูลส่วนตัวที่ `/account/profile` ผู้มี role `admin` หรือ `super_admin` เห็นทางเข้าหลังบ้านจากหน้าร้านและสลับไปมาโดยคง session เดิม เส้นทางและกฎข้อมูลปฏิเสธผู้ไม่มีสิทธิ์จริง

## User Stories

1. ในฐานะผู้มาเยือน ฉันต้องการเปิดฟอร์มล็อกอินจากหน้าร้านได้โดยตรง เพื่อเข้าสู่บัญชีเมื่อฉันต้องการ
2. ในฐานะเจ้าของบัญชี ฉันต้องการเข้าสู่ระบบด้วยข้อมูล Firebase Authentication เดิม เพื่อใช้บัญชีที่มีอยู่
3. ในฐานะเจ้าของบัญชี ฉันต้องการเห็นข้อผิดพลาดเมื่อข้อมูลล็อกอินไม่ถูกต้อง เพื่อแก้ไขและลองใหม่
4. ในฐานะเจ้าของบัญชี ฉันต้องการเห็นสถานะกำลังเข้าสู่ระบบและป้องกันการกดซ้ำ เพื่อเข้าใจผลของคำขอ
5. ในฐานะเจ้าของบัญชี ฉันต้องการกู้รหัสผ่านด้วยอีเมลของบัญชี เพื่อกลับมาใช้งานได้
6. ในฐานะผู้มาเยือน ฉันต้องการสมัคร Customer account ได้ เพื่อจัดการข้อมูลส่วนตัวภายหลัง
7. ในฐานะลูกค้าที่เข้าสู่ระบบ ฉันต้องการไป `/account` ซึ่งเป็นภาพรวมบัญชี เพื่อดูทางเลือกในบัญชี
8. ในฐานะลูกค้าที่เข้าสู่ระบบ ฉันต้องการไป `/account/profile` เพื่อดูและแก้ข้อมูลส่วนตัว
9. ในฐานะผู้ใช้ที่เปิดหน้าเฉพาะบัญชีก่อนล็อกอิน ฉันต้องการกลับไปหน้าที่ตั้งใจเปิดหลังเข้าสู่ระบบ เพื่อทำงานต่อ
10. ในฐานะผู้ใช้ที่โหลดหน้าใหม่ ฉันต้องการให้ระบบตรวจ session ก่อนแสดงหน้าที่ป้องกัน เพื่อไม่ถูกส่งไปล็อกอินทั้งที่ยังมี session
11. ในฐานะผู้ใช้ ฉันต้องการออกจากระบบและให้หน้าที่ป้องกันกลับไปขอเข้าสู่ระบบ เพื่อควบคุมบัญชี
12. ในฐานะผู้ดูแลระบบ ฉันต้องการใช้บัญชีเดียวกันที่หน้าร้านและหลังบ้าน เพื่อไม่ต้องสร้างหรือเข้าบัญชีอีกชุด
13. ในฐานะผู้ดูแลระบบ ฉันต้องการให้ระบบรู้ role จากบัญชีจริงโดยไม่ต้องเลือก `admin` หรือ `super_admin` ในฟอร์ม เพื่อไม่ถูกปฏิเสธเพราะเลือกผิด
14. ในฐานะผู้ดูแลระบบ ฉันต้องการเห็นทางเข้าหลังบ้านเมื่อ role อนุญาต เพื่อไปทำงานได้
15. ในฐานะผู้ดูแลระบบ ฉันต้องการสลับระหว่างหน้าร้านกับหลังบ้านโดยคง session เดิม เพื่อทำงานต่อเนื่อง
16. ในฐานะลูกค้าทั่วไป ฉันต้องการไม่เห็นทางเข้าหลังบ้าน เพื่อให้เมนูตรงกับสิทธิ์ของฉัน
17. ในฐานะลูกค้าทั่วไป ฉันต้องการให้การเปิด URL หลังบ้านโดยตรงถูกปฏิเสธ เพื่อไม่เห็นข้อมูลผู้ดูแลระบบ
18. ในฐานะเจ้าของบัญชีที่ถูกระงับ ฉันต้องการเห็นการปฏิเสธที่ชัดเจน เพื่อทราบว่าไม่สามารถใช้งานพื้นที่ป้องกันได้
19. ในฐานะเจ้าของร้าน ฉันต้องการให้การแก้ role ในหน้าเว็บหรือการเลือกปุ่มใด ๆ ไม่เพิ่มสิทธิ์จริง เพื่อป้องกันการเข้าถึงโดยไม่มีสิทธิ์
20. ในฐานะเจ้าของร้าน ฉันต้องการให้กฎ Firestore ตรวจ role ที่เชื่อถือได้และไม่มีข้อยกเว้นตามอีเมล เพื่อควบคุมข้อมูลหลังบ้าน
21. ในฐานะผู้ใช้ ฉันต้องการเห็นสถานะที่เข้าใจได้เมื่อการตั้งค่า Firebase หรือข้อมูลโปรไฟล์ขาดหาย เพื่อไม่พบหน้าค้างหรือสิทธิ์ผิดพลาด

## Implementation Decisions

- ใช้ Firebase Authentication ชุดเดียวกันสำหรับ `customer`, `admin` และ `super_admin`; role และสถานะบัญชีอ่านจากข้อมูลที่ระบบควบคุม ผู้ใช้ไม่กำหนด role ผ่านฟอร์มหรือ client state
- ปรับฟอร์มล็อกอินหลังบ้านให้ไม่ต้องเลือก role และนำทางตามสิทธิ์จริง หากใช้ฟอร์มหน้าร้านเข้าสู่บัญชี admin ก็ยังต้องเข้าหลังบ้านได้ผ่านทางเข้าที่แสดงตาม role
- การสมัครบัญชีผ่านหน้าร้านสร้าง Customer account ที่มี role `customer` เท่านั้น การเลื่อนสิทธิ์เป็น admin ไม่อยู่ในแบบฟอร์มสาธารณะ
- `/account` เป็นภาพรวมบัญชี; `/account/profile` เป็นพื้นที่จัดการข้อมูลส่วนตัว หน้าล็อกอินเปิดฟอร์มโดยตรง ไม่มีหน้าเกริ่น
- เมื่อผู้ใช้พยายามเปิดหน้าบัญชีที่ต้องล็อกอิน ให้จำปลายทางที่ปลอดภัยและกลับไปหลังเข้าสู่ระบบสำเร็จ
- แสดงปุ่มไปหลังบ้านเฉพาะบัญชีที่มี role `admin` หรือ `super_admin` และสถานะอนุญาต ปุ่มเปลี่ยน route โดยคง session; หน้า admin ทุกหน้าต้องตรวจสิทธิ์แยกจากการแสดงปุ่ม
- ใช้ role จริงทั้งใน route guard และกฎ Firestore; นำข้อยกเว้น admin ตามอีเมลออก
- ระหว่างโหลด auth และโปรไฟล์ ให้แสดงสถานะรอ เมื่อโปรไฟล์ขาดหายหรืออ่านไม่ได้ ให้ปฏิเสธการเข้าพื้นที่ที่ต้องใช้ role จนกว่าจะตรวจสิทธิ์ได้
- ยังไม่เพิ่ม Firebase Anonymous Authentication ในระยะนี้ เพราะยังไม่มี guest checkout ที่สร้าง Order

## Testing Decisions

- ทดสอบพฤติกรรมที่ผู้ใช้เห็นและสิทธิ์ที่ระบบบังคับจริง ไม่ผูกกับชื่อคอมโพเนนต์หรือ state ภายใน
- จุดทดสอบหลักคือ เข้าสู่ระบบ → โหลด role → เปิดบัญชีหรือหลังบ้าน → สลับพื้นที่ → ออกจากระบบ โดยใช้ Firebase Emulator สำหรับ Authentication และ Firestore ตรวจสิทธิ์ปลายทาง
- ตรวจ customer, admin, super_admin, ผู้ไม่เข้าสู่ระบบ, บัญชีถูกระงับ, โปรไฟล์หาย และอ่านโปรไฟล์ล้มเหลว
- ตรวจว่าฟอร์มไม่ต้องเลือก role และบัญชี admin ใช้ได้ทั้งหน้าร้านกับหลังบ้านโดยไม่ล็อกอินซ้ำ
- ตรวจการเปิด URL หลังบ้านโดยตรง การแก้ role ฝั่ง client และการอ่าน/เขียน Firestore โดยตรงด้วย customer ว่าไม่เพิ่มสิทธิ์
- ตรวจว่าการแก้ role ในโปรไฟล์ตนเองผ่าน Firestore ถูกปฏิเสธสำหรับ customer
- ตรวจการสมัครใหม่ได้ role `customer`, การกู้รหัสผ่าน, ข้อมูลล็อกอินผิด, การกดซ้ำ, โหลดหน้าใหม่ และการออกจากระบบ
- ตรวจการกลับไปหน้าเดิมหลังล็อกอิน โดยไม่รับปลายทางที่พาออกนอกพื้นที่ที่ผู้ใช้มีสิทธิ์
- ใช้แนวทางตรวจ route ในเบราว์เซอร์จากงานโครงหน้าร้านเดิม; ยังไม่มีชุดทดสอบ UI ที่ commit ไว้ จึงเพิ่มการทดสอบที่เส้นทางผู้ใช้และกฎ Firebase เป็นหลัก

## Out of Scope

- การสร้าง Order, guest checkout, การชำระเงิน, การคำนวณราคา/สต็อก/ค่าจัดส่ง และผลสั่งซื้อจริง
- ประวัติคำสั่งซื้อ การติดตาม Order ของ guest จากเครื่องอื่น การเชื่อม Order guest เข้าบัญชี และ dashboard คำสั่งซื้อจริง
- Firebase Anonymous Authentication สำหรับผู้ซื้อ guest
- การปรับสิทธิ์ Storage สำหรับรูปสินค้า ซึ่งต้องจัดการก่อนเปิดใช้ส่วนสินค้าในสภาพแวดล้อมจริง
- การสร้างระบบจัดการ role สำหรับผู้ดูแลระบบ; ให้เตรียมบัญชีทดสอบ role ผ่าน Emulator
- การเปลี่ยนโครงหน้าร้านจอคอมพิวเตอร์ที่ทำไปแล้ว นอกเหนือจากจุดนำทางและสิทธิ์บัญชี

## Further Notes

- แผนต้นทางยังคงเป็นแหล่งอ้างอิงของระยะซื้อขายถัดไป โดยมีเรื่องต้องตัดสินใจก่อนลงมือ ได้แก่ วิธีชำระเงินและจุดที่ถือว่าชำระสำเร็จ ช่องทางพิสูจน์สิทธิ์ guest ข้ามเครื่อง และการเชื่อม Order guest กับบัญชี
- หน้า checkout และหน้าคำสั่งซื้อปัจจุบันยังไม่ใช่หลักฐานว่ามีการซื้อขายจริง ระยะนี้ไม่ถือว่ามี Order ที่บันทึกแล้ว
- ไม่พบ ADR ในพื้นที่บัญชีและสิทธิ์ หากมีการนิยามสถานะบัญชีหรือคำศัพท์สิทธิ์เพิ่มเติม ให้บันทึกใน glossary ก่อนใช้หลายความหมาย
